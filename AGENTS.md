# AGENTS.md — envio_ga-indexer

Mirrors a Hasura / Envio HyperIndex GraphQL API (Gnosis Chain: Circles, Metri, Metri Pay, Gnosis Pay / Cashback, Investment) into ClickHouse.
Production data flow: GraphQL list queries (id-keyset, or `(cursor_field, id)` for field_cursor; 1000-row cap; `Authorization: Bearer` by default — `src/config.py:27-28`, `src/services/graphql_client.py:73-74,150-201`) → `python -m src.main load realtime` → ClickHouse database `envio_ga`: `raw_entities` (append-only JSON audit log, no TTL), one ReplacingMergeTree typed table per entity, `ga_index_state` (all progress). The source is mutable in place, deletes rows and exposes no cursor, count or delete signal — every design choice follows from that.
The one rule: **never `FINAL` on any `envio_ga` table** (it OOMs the instance). Read with `argMax(col, insert_version) ... GROUP BY id HAVING argMax(_deleted, insert_version) = 0` (`src/cli.py:72-75`).
Derive, do not recall: entity counts (28 entities, 2 block_cursor / 4 dual / 8 field_cursor / 14 full_rescan, 18 deletable, 6 with a block field) come from `src/registry/generated.py`; only the totals 28 and 18 are pinned by tests (`tests/test_registry.py:12,57`). Re-derive them; do not trust numbers in prose, including here.

## Where this runs (production)

GKE Autopilot, deployed by Terraform from the private deployments repository `gnosisdevops/infrastructure-gnosis-analytics`. Image `ghcr.io/gnosischain/gc-envio-ga-indexer`, built on every push to `main` and tagged both `latest` and the short commit SHA (`.github/workflows/build-and-release.yml:45-55`); production pins a SHA tag, never `latest`.

| Role | What it runs | Schedule | Writes (database.table) |
|---|---|---|---|
| Continuous writer — one Deployment, 1 replica, `Recreate` strategy | `python -m src.main load realtime` (no `--entities`; `ENABLED_ENTITIES` unset = all 28) | continuous; `POLL_INTERVAL=30` s tick, entities processed sequentially | `envio_ga.raw_entities`, all 28 `envio_ga.<entity>` typed tables, `envio_ga.ga_index_state` (`partition_key` `realtime` / `rescan`) |

Production env (values, not secrets): realtime gets `CLICKHOUSE_DATABASE=envio_ga CLICKHOUSE_PORT=443 CLICKHOUSE_SECURE=true LOG_LEVEL=INFO METRICS_ENABLED=true METRICS_PORT=9090 GQL_MAX_RPS=10 PAGE_SIZE=1000 POLL_INTERVAL=30 REALTIME_OVERLAP_BLOCKS=5 RESCAN_INTERVAL_S=300` (`RESCAN_INTERVAL_S` has no effect, see below); reconcile gets the first seven only. `CLICKHOUSE_HOST/USER/PASSWORD`, `GRAPHQL_ENDPOINT`, `GRAPHQL_API_KEY` come from a cluster secret. Everything else is the code default in `src/config.py:23-62`, plus `FORCE_JSON_LOGS` (default false, `src/utils/logger.py:15`; unset in production, so logs are single-line console format, `logger.py:29-36`). Memory: realtime 512Mi request / 1Gi limit; reconcile 256Mi / 512Mi.

- **Local-only artifacts:** `Makefile`, `docker-compose.yml`, `docker-entrypoint.sh`, `.env` / `.env.example`, `scripts/*.py` run as scripts. Production runs only the image's CLI; both workloads set the container `command`, which replaces the image `ENTRYPOINT` (`Dockerfile:19`), so `docker-entrypoint.sh` never executes in production.
- **Single-writer rule:** exactly one `load realtime` process. Realtime is one sequential loop over every selected entity with no lease, lock, heartbeat or shard (`src/services/loader.py:154-168`); sharding exists only for backfill work items (`loader.py:3-4`). One replica is required because a second instance permanently duplicates `raw_entities` versions and doubles the GraphQL load (Hazards), and it is enforced only by the Deployment (1 replica + `Recreate`). `reconcile` is designed to run beside it: an `insert_version` fence exempts rows realtime touched mid-walk (`src/services/maintenance.py:61,97-100`).
- **Deliberately not deployed:** `load backfill`, `migrate`, `maintain *`, `status`, `reconcile --loop`, `introspect`. The old cluster's migration / backfill / maintenance one-shot Jobs were not ported. One-shot work runs through the runbook's one-shot job procedure, never inside the realtime pod.
- **Restart:** safe; realtime resumes from each entity's `realtime`/`rescan` row in `ga_index_state` (`src/services/state.py:115-137`), and a rescan is not re-run until its interval has passed (`loader.py:263-267`). Never delete an entity's `realtime` row: with no watermark it bootstraps from an unscoped `SELECT max(...) FROM <typed table>` (`loader.py:190-191,212-213,282-290`), a full aggregate on `transfer` or `transaction_action`.
- **No workload runs `migrate`**, not even on start: the entrypoint only waits for `SELECT 1` (`docker-entrypoint.sh:6-23`) and production bypasses it anyway. A schema change needs a human-run one-shot `migrate`, then a writer restart.
- **Production change path:** the image pin, env values, replica count and cron suspend live in the stack's locals file in the private deployments repository. A human edits it, reviews a plan and applies. A manual scale or patch on the cluster is drift that the next apply silently reverts (private `runbooks/README.md:92-93`).

## What does not exist, or does not do what its name says

- **"Stuck pages" is always empty.** `claim_page` (`src/services/state.py:61`) has no caller, so no row is ever `claimed`; `recover_stuck_pages` (`state.py:149-162`) and the check's `stuck` section (`maintenance.py:177`) are dead.
- **`pending` is write-only.** `requeue_page` / `recover_stuck_pages` write it (`state.py:159,165`); nothing reads it — `resume_position` reads only `completed` (`state.py:91-95`). `maintain reset --status` and the requeue half of `maintain fix` change nothing a backfill consumes, but they do hide those pages from `check` and `fix` (`state.py:140-147`); the only real re-drive is the backfill `fix` launches (`maintenance.py:214-221`).
- **`load backfill` exits 0 on failure.** A fetch or insert error records a `failed`/`dead` page and returns from that item (`loader.py:114-119,131-137`); the run still logs `Backfill complete` (`loader.py:79`). Read `maintain check`, not the exit code.
- **An unknown `--entities` name selects nothing and succeeds.** `_select` filters silently (`loader.py:293-298`; `maintenance.py:36-41`), so a typo yields `Backfill complete` over zero items. Names match case-insensitively against either the table name or the GraphQL type name (`loader.py:296-297`; `maintenance.py:39-40`; the same rule for `ENABLED_ENTITIES`, `overrides.py:23-24`), so `trust_relation`, `TrustRelation` and `trustrelation` all select `trust_relation`.
- **`ENABLED_ENTITIES` filters every entity-selecting verb, not just realtime** (`src/registry/overrides.py:18-25`, called by `loader.py:293-298` and `maintenance.py:36-41`). A value in `.env` (loaded on import, `src/config.py:9`) narrows `load *`, `reconcile` and `maintain *`, and `--entities` is intersected with it, so an excluded name selects nothing and exits 0. "Default = all 28" in this file means "all `enabled` and `ENABLED_ENTITIES`-listed".
- **A broken `src/registry/generated.py` is silent.** `overrides.py:12-15` swallows the import error and uses an empty registry, so every verb runs over zero entities and exits 0 (realtime idles). After `introspect`, check `python -c 'from src.registry.generated import ENTITIES; print(len(ENTITIES))'` before deploying.
- **`PAGE_SIZE` only reaches `load backfill`** (`loader.py:58`). Realtime, rescan and reconcile use `spec.page_size`, baked at codegen time (`scripts/introspect.py:194`; `loader.py:198,228,272`; `maintenance.py:69`).
- **`RAW_TTL_DAYS` is parsed and used nowhere** (`src/config.py:57` is its only occurrence); `raw_entities` has no TTL (`migrations/002_raw_entities.sql:14-16`). `README.md:410` claims it adds one.
- **`RESCAN_INTERVAL_S` is parsed and used nowhere** (`src/config.py:44` is its only occurrence). The rescan cadence is `spec.rescan_interval_s` (`loader.py:266`), baked into `src/registry/generated.py` by `introspect` from `config/entities.yaml:28` (default 300) and the per-entity overrides (`scripts/introspect.py:179`). Production's `RESCAN_INTERVAL_S=300` has no effect; `README.md:406` is wrong. To change a cadence, edit `config/entities.yaml`, run `introspect`, and redeploy.
- **`envio_ga_entity_staleness_seconds` is only ever set to 0** (`loader.py:184`) and never counts up; an entity that errors every tick never gets the label (`loader.py:173-186`), so a staleness alert cannot see it. `envio_ga_entity_rows` is declared (`src/observability.py:59-63`) and never set.
- **`/health` never returns 503.** Its only writer is `update_health(status="ok")` at CLI start (`src/cli.py:88`); 503 needs `failed`/`error` (`observability.py:127`). Both production probes point at `/health`, so a wedged loop stays Ready.
- **`ga_index_state.strategy` / `status` are `LowCardinality(String)`** (`migrations/001_state_tables.sql:9,13`; `003:42,47`); `README.md:246,250` still shows `Enum8`. The `003` header records the byte-0 corruption that forced the change.
- **`migrate` never adds a column to an existing table** (`CREATE TABLE IF NOT EXISTS`); an `introspect` `NEW field` line means a manual `ALTER TABLE ... ADD COLUMN` (`scripts/introspect.py:317`).
- **`maintain check` silently drops its coverage section** when the head call fails: `_source_head` swallows every exception and returns 0 (`maintenance.py:137-138`), and `chunk_coverage` returns `None` for head 0 (`maintenance.py:143`).
- **`maintain fix` comment says "one entity expected when a range is given"** (`maintenance.py:199`) but the loop applies the range to every selected spec (`maintenance.py:203-211`).
- **`README.md:464` "two long-lived services: realtime and `reconcile --loop`"** — production runs reconcile as a daily one-shot CronJob, not `--loop`.
- **The committed registry can be ahead of, or behind, the upstream schema.** On 2026-09-09 four entities failed GraphQL validation on every poll (`avatar` `trustsGivenCountV1`, `token` `version`, `trust_relation` `isMigrated`, the `V1TokenPendingStop` root field) while still listed in `src/registry/generated.py:15-22,204-211,240-247,249-256`; they were silently not syncing. The list has not been re-checked since 2026-09-09: run `introspect` locally and read the drift before any fix and before trusting any entity.

## Hazards

- `maintain fix`, with or without a range, launches a 4-worker backfill if any failed/dead page exists (`maintenance.py:186-197,213-221`; `loader.py:57`) — in the 1Gi realtime pod that is the OOM. `--dry-run` first, `--entities` always, one-shot job only. Runbook: "Corrupt range".
- A one-shot `maintain` job is cloned from the reconcile CronJob, which is sized 256Mi / 512Mi for an id-diff sweep, and must be raised to 512Mi request / 1Gi limit while rendering, because `fix` can launch a 4-worker backfill (private `runbooks/60-gke-one-shot-jobs.md:140,145-146`). If the entity is one realtime is actively writing, a human pauses realtime first; that pause is the only sanctioned scale of the continuous Deployment, and the next apply reverts it (`60-gke-one-shot-jobs.md:148-156`). Runbook: one-shot jobs, envio.
- `--block-range` deletes the window then hash-skips unchanged payloads (`maintenance.py:229,236`; `graphql_entity.py:49-53`): a corrupt-but-unchanged range becomes an empty one, across all 6 block-bearing tables if `--entities` is omitted. Record the window's live row count first. Runbook: "Corrupt range".
- `maintain reprocess` re-inserts every id's latest raw payload with `_deleted=0` (`parsers/generic.py:20`; `maintenance.py:280-294`). `raw_entities` holds no delete record (`graphql_entity.py:66-72`), so on the 18 deletable entities every row deleted upstream reappears as live until the next reconcile re-tombstones it (`maintenance.py:97-115`); only reconcile ever writes `_deleted=1`, so the 10 non-deletable entities have no tombstones to lose unless one was reconciled while it was still flagged deletable (the runbook's warning is wrong). No range flag; it walks the whole raw history. Run `reconcile` for the same entities right after it. Runbook: "Re-derive typed tables".
- `maintain reset` (no `--status`) and `load backfill --restart` delete all backfill resume state for the selected entities, default all 28 (`maintenance.py:266-268`; `loader.py:66-69`). `maintain reset --status completed` loses it too (every completed page becomes `pending`, `state.py:91-95`) and also zeroes the realtime watermark and rescan marker (`state.py:129-137,164-166`).
- `status` runs an unscoped aggregate over `ga_index_state` plus an unscoped `count()` per backfilled entity's table (`cli.py:65-75`; `state.py:187-198`) — never against production. Runbook: "Safe stop and restart".
- `reconcile --entities transfer|transaction|transaction_action` does nothing (skipped, `maintenance.py:48`); never flip them `deletable` — a 100M-row id-walk is not viable. Runbook: "Reconcile".
- A manual `reconcile` while the nightly run is live drops the other's stage table (`maintenance.py:62,121`); the cron is `Forbid`, you are not.
- `migrate` while the writer runs re-flips `ga_index_state` column types; the writer's cached types then corrupt the table (`migrations/003_fix_strategy_enum.sql:18-22`). Restart the writer after any migrate.
- A second `load realtime` (including a laptop compose `realtime` pointed at production) permanently duplicates `raw_entities` versions and doubles the GraphQL and ClickHouse load: both instances walk and rescan every entity, each write's hash read (`graphql_entity.py:49-51`) and insert (`graphql_entity.py:76-77`) run with no lock between them, so a change both instances read before either inserts is written twice into `raw_entities`, which is append-only and never deduplicated (`migrations/002_raw_entities.sql:1-2,14`); their watermark rows also interleave in `ga_index_state`. There is no lease or lock in `loader.py:154-168`.
- A partial reconcile walk tombstones nothing: a fetch or insert error raises out of the walk, the stage is dropped (`maintenance.py:120-121`) and the sweep logs `Reconcile entity failed` and moves on (`maintenance.py:56-57`). The `Reconcile walk incomplete; skipping tombstone` branch (`maintenance.py:83-85`) is unreachable, because both loop exits set `walk_finished=True` (`maintenance.py:70-78`); the runbook calling that message the safety mechanism is wrong. Never add a path that tombstones from a partial walk.
- `FINAL` on any `envio_ga` table OOMs the instance. Runbook: opening section.

## Health and verification is a warehouse query

```sql
SELECT entity, partition_key,
       argMax(cursor_end, insert_version)          AS watermark,
       max(created_at)                             AS last_written,
       dateDiff('second', max(created_at), now())  AS age_s
FROM envio_ga.ga_index_state
WHERE partition_key IN ('realtime', 'rescan')
GROUP BY entity, partition_key
ORDER BY age_s DESC;
```

Healthy: all 14 cursor-tier entities (2 block_cursor + 4 dual + 8 field_cursor) show a `realtime` row a few minutes old — a tick writes the watermark row even when nothing changed (`loader.py:205,258`), and ticks are sequential over 28 entities so one can exceed `POLL_INTERVAL=30` s; the 18 rescan-writing entities (14 full_rescan + 4 dual) show a `rescan` row younger than about 2x their `rescan_interval_s` (300 s from `config/entities.yaml:28` via `scripts/introspect.py:179`, not the env; 1800/3600/7200 overrides in `config/entities.yaml:48,53,58,65,115`). An entity old or missing here while the rest are fresh is failing every tick (`loader.py:185-186`): grep its logs for `Realtime entity error`. Known exception: as of 2026-09-09, `avatar`, `token`, `trust_relation` (both rows — the dual block sync raises before the rescan, `loader.py:179-181`) and `v1_token_pending_stop` (rescan row) fail GraphQL validation every tick, so they show stale here (not re-checked since). That is the registry-drift defect above, not a new outage; re-check with `introspect`.
Is it us or the source: for the 6 block_cursor/dual entities (`transfer`, `transaction`, `avatar`, `token`, `trust_relation`, `guardian_module`) the `realtime` watermark is the source head at tick time (`loader.py:179-181,205`; head from `chain_metadata`, `graphql_client.py:142-147`). Fresh `age_s` with a watermark flat across two runs means the source halted (runbook: nothing to fix here); stale `age_s` means us. If every entity is stale at once, grep for `Realtime tick error`: the head call failed and the whole tick aborted (`loader.py:162,168-169`). The head-stalled alert (source head not advanced in 30 min) fires on a source halt as well as on ours; read it that way (runbook: "Is it us, or is the source halted?").
Coverage / gaps: `python -m src.main maintain check --entities ⟨X⟩` from a one-shot job — the only honest completeness signal (min over chunks). Only `transfer`/`transaction` have chunks, `stuck` is always empty, the coverage section vanishes when the head call fails, and a never-backfilled entity is absent rather than INCOMPLETE.
Not a health signal: pod Running/Ready (`/health` never 503s), exit 0 (backfill and reconcile isolate failures), row counts (runbook), `envio_ga_entity_staleness_seconds` (pinned at 0), `envio_ga_reconcile_*` (the cron pod is not scraped — the stack's PodMonitor selects the realtime pod only), silent logs (a no-change tick logs nothing, `loader.py:207,260`; `Realtime rescan` logs unconditionally, `loader.py:280`).
